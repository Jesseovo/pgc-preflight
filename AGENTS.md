# PGC Preflight

## Product contract

- A website for batch preflight checks of single-file HTML games; target domain `pgc.ovoxin.top`.
- The legacy root preflight API checks basic loading, obvious runtime faults, input response, obvious mobile layout defects, and reachable restart flows.
- The current Forge AI simulation review follows the migrated PGC Forge contract: the model scores aesthetics, ease of play and playability from 1–3 each, uses the platform calibration set, and writes evidence-backed fixes. This is a simulation score, not the final human decision.
- All game-review findings and verdicts come from the configured vision model. Code only validates uploads, runs the browser, gathers evidence, executes bounded model actions and validates report format. Never add rule-based game judgments as a fallback.
- A check that could not be verified is `review`, never an automatic pass or failure. If no model is configured, refuse to start review rather than generate a report.
- Do not treat screenshot changes in an animated game as proof that input worked.
- Uploaded HTML is untrusted. Keep it in a separate browser context, restrict navigation and outbound resources, close browsers in finally, and never run it in the app origin.
- `/admin` manages up to 24 saved model profiles with a display name, endpoint, model ID, protocol, enabled state, image capability and encrypted API key. DeepSeek and Claude Opus remain preset entries. Each profile has one Key; independent profiles can use the same model with different Keys. Never echo keys in responses or logs. The model selector exposes exactly two groups: AI review (`review`, including verification) and other functions (`create`, including expansion, briefs, previews, assets, game production, tagging and vocabulary). All stages resolve through these two groups; ignore legacy per-stage overrides and remove them on route save. The other-functions selection is also saved as the compatibility default. Save both groups atomically, and reject deletion of an active or used profile. A profile marked `vision: false` receives review requests without screenshots plus an explicit note that visual judgement rests on source and run log; do not silently drop images for a vision profile. The legacy root preflight keeps using the active profile.
- `/admin` also creates member accounts, resets passwords, enables/disables accounts and grants/revokes `canReview`. `/login` is for members. `/api/check` must validate session and current review permission on the server. Role changes, account disablement and password resets revoke old sessions.
- Opening `/` or `/index.html` without a valid session redirects to `/login` before any workspace renders. An administrator is routed to `/admin`, and a member stays at `/` for AI simulation review; the old root upload view is no longer a user-facing entry. Keep public and member views free of links to `/admin`; the administrator can visit that path directly.
- Visual direction follows Jesseovo's GitHub profile: white surfaces, fine borders, muted sage accents, compact layouts and the original pixel cat. Avoid garden backgrounds and oversized decorative cards. Profile artwork is copied into `public/artwork/`.
- Keep uploads, screenshots and reports ephemeral. Never commit real team game files or internal research data.

## PGC Forge integration

- The full migrated Forge workbench is embedded inside `/admin`; members use AI simulation review directly at `/`. `/forge` is an administrator-only compatibility document for the embed, and `/review` redirects to the appropriate canonical page. Their backend behavior, prompts, weighting, topic library, work library, brief generation and AI simulation review follow `C:\Users\Administrator\Desktop\05 Riffle\pgc-forge`. All Forge model calls use the encrypted profiles and purpose routes configured in `/admin`; Forge settings must not expose a second model or API key configuration.
- The legacy root PGC Preflight API remains available only for compatibility. Members only receive the Forge AI simulation review surface; administrators receive the complete Forge workbench.
- The Forge surface uses the existing PGC Preflight visual language: white surfaces, fine borders, muted sage accents, compact layouts and the pixel cat artwork.

## Development

- `npm run dev`: website plus local browser-check API. Requires local Chrome or Edge; set `PGC_CHROME_PATH` if needed.
- `npm run build`: typecheck and production build.
- `npm test`: validation, network policy, and verdict regression tests.
- `npm run test:runtime`: real-browser integration against synthetic fixtures and scripted model responses; does not validate real model accuracy.
- `npm run deploy`: Cloudflare Worker assets, Browser Rendering and D1 settings, custom domain configured in `wrangler.jsonc`. Initialize D1 migrations and `ADMIN_PASSWORD` / `SETTINGS_KEY` secrets before deployment.

## Background generation

- Topic expansion, brief generation and asset generation run through `pgc-forge-jobs`, with consumer concurrency 1 and short HTTP enqueue responses. Keep the D1 lease heartbeat and recoverable error states. Brief and assets share `startTopicJob` on the server and `generateTopicJob` in `public/forge/app.js`.
- Administrators can start a game from an expanded candidate with “开始制作”; use the enabled, configured `game` route with the same fallback as other creation stages. A `game` Queue message carries a unique request ID. Claim `queued` → `running` atomically, ignore duplicate/old messages, maintain a heartbeat, and use one 12-minute deadline for HTML generation. Never implicitly generate a full brief: expanded topic data already supplies the playable core, and the mandatory long-brief step exhausted output tokens for production topic 31 before HTML generation. A failed task requires explicit retry with a new request ID; browser refresh only observes persisted state. Queue wait is distinct from a running lease.
- Completed games live on the topic in `product_html` and appear in the administrator-only “成品” tab. Status/list endpoints omit HTML. Previews use a separate `sandbox allow-scripts` document with network disabled and never `allow-same-origin`; downloads are attachments. Production migration `0009_products.sql` is required. `npx tsx scripts/verify-products.ts` verifies submission deduplication, refresh/reconnect, stages, retry, isolated play, downloads and mobile layout against controlled responses.
- Game generation targets a compact playable first version (under 220 lines and 15KB excluding existing asset libraries, in the prompt) with a 32,768-token budget shared by adaptive thinking and HTML. The Anthropic Opus transport explicitly allows this above its old 24k clamp; other model caps and review budgets stay unchanged. On 2026-10-27, production Misprint exhausted 16k before text, while the same input at 32,768 completed in 283s with 14,634 HTML characters. Streamed character counts update waiting feedback at most once per five seconds without exposing partial source. A truncated game fails explicitly and is never automatically regenerated under a fresh paid request; the user chooses retry.
- The first version uses the expanded topic's concept, core loop, controls, art direction and palette; if these are absent, `gameBrief` selects the saved brief's F1–F4 identity/art/controls/core loop. The full brief and downloadable contract remain intact. The UI must describe the result as a playable first version, with late bosses and expansion stages reserved for later iterations. Full long-brief Opus live attempts returned thinking until the token cap even with low effort, so do not claim that complete production specifications have been validated by the short diagnostic.
- Riffle's authenticated `/v1/models` advertises Opus 5.5 adaptive thinking and `output_config.effort` values `low`, `medium`, `high`, `xhigh`, `max`; game generation on the Anthropic `claude-opus-5-5` route explicitly requests `thinking: {type: 'adaptive'}` together with `output_config: {effort: 'low'}` to bound first-version planning latency. Sending effort alone returned only thinking and then hit the token cap in live tests; the explicit pair returned a small diagnostic game successfully. Do not send unsupported `thinking: disabled` to this model or send these Opus-specific controls to other models. Keep other workflows' inference controls unchanged.
- Asset generation (after a brief exists) produces one self-contained HTML file: an art review sheet whose `<script id="game-assets">` block defines `GAME_ASSETS` drawing functions that the game copies verbatim. It is model-generated HTML: preview it only in an `allow-scripts` sandbox without `allow-same-origin`, serve downloads as attachments with `Content-Security-Policy: sandbox`, and strip external resources before saving. When assets exist, the brief download appends section H telling the game builder to use them.
- Long model retries must fit within the Queue consumer lifetime; never reintroduce browser-side cross-tab locks.
- Batch AI review uses the separate `pgc-review-jobs` Queue, with at most 3 concurrent consumers. The browser captures each game's three phone frames sequentially, pipelines captured games to background model jobs, and tracks each result independently. Never change Forge scoring prompts or calibration to implement queue transport.
- `/api/forge/review/probe` captures four real Chromium viewport images, including DOM/CSS and all Canvas layers, in three isolated phone pages with distinct origins. Keep trusted touch gestures sequential within a browser. Never restore largest-Canvas copies or treat a layer's bounds as whole-page coverage. Capture failure means no score.
- Scores must include model-written `score_reasons` for each dimension and `uncertainties`. Separate observed screenshots/logs from source inference; a single touch and short observation do not verify feel, listening, full game loops or long-term pacing. Do not deduct simply because something was not tested. Existing reports keep their historical scores and require re-upload for new evidence.
- Before publishing a review, the same AI review model rechecks the initial draft in a `review_verify` stage against the same original evidence and calibration. Verify the AI review profile is enabled and configured before enqueueing. Both stages share a 12-minute deadline, model throttling and distinct idempotency keys. DeepSeek receives its 24k budget independently in each stage. Do not publish an unverified draft when the second stage fails; never substitute code-authored score adjustments. Show evidence verification as a waiting stage.
- Review input is temporarily stored in `review_inputs` in small D1 chunks, removed after success/failure, and purged after 24 hours by the hourly scheduled handler. Completed reviews retain the existing report/evidence behavior. Never store the original HTML permanently.
- `npx tsx scripts/verify-review.ts` verifies multi-file picker and page-wide drag/drop, bounded concurrent model submissions, isolated retry, report actions, mobile overflow, and the real browser probe using synthetic reports.
- Review UI shows batch status counts, stages, failed-item retries reusing captured evidence, loaded batch report export, and searchable/filterable history. Keep the progress tray compact by default for review jobs so it cannot cover batch actions; respect an explicit user toggle.
- `npx tsx scripts/verify-model-routing.ts` verifies model profile and Key management through the actual admin API with an isolated store, exactly two group selectors, correct stage inheritance, route persistence, deletion protection, retained editor input, and desktop/mobile layout without provider requests.
- `npx tsx scripts/verify-review-evidence.ts` verifies real DOM/multi-Canvas pixels, trusted touch, DOM-only and Canvas-only capture, resource restrictions and context cleanup. Synthetic fixtures verify evidence collection, not real-world score accuracy.
- All user-visible asynchronous operations need waiting feedback. Use the shared `public/forge/progress.js` component (also loaded by `src/progress.ts`); count real completed items/checkpoints when known, and use an indeterminate bar plus stage and elapsed time for model calls. Never estimate model completion percentages from elapsed time. Embedded Forge tasks appear in the parent admin viewport.
- `npx tsx scripts/verify-progress.ts` verifies brief progress, reconnect/retry, duplicate-click prevention, background completion, regeneration, mobile/reduced-motion behavior, iframe feedback, model tests and login waiting against controlled responses.
- Riffle currently limits the configured key to 10 requests/minute (`KEY_RATE_LIMIT`). All production calls, including admin connection tests, share D1 pacing in `model_throttle` (7 seconds between starts). Honor provider `Retry-After`, share cooldowns and keep 429 retries in the transport layer only. Pending waits belong in progress feedback; never change scoring prompts to work around limits.
- Preserve the redacted upstream reason/code for HTTP 409. Retry only an explicit idempotency/request-pending code with the same key; budget-reservation and unknown conflicts must not be blindly retried. Historical generic 409 records do not identify the original conflict cause.
- Official DeepSeek calls use streaming; structured responses request JSON mode. AI simulation review keeps thinking enabled with low effort and a 24,000-token budget shared by thinking and report text. Never treat reasoning content as a report. Detect length truncation and incomplete streams explicitly. Validate the complete review structure inside the bounded generation retry; malformed completed output can be regenerated with field feedback and a fresh request key, while unknown interrupted requests must not be automatically replayed.
- Failed review tasks stop their elapsed clock, say that review is incomplete, and offer retry. Retry in the current page reuses captured evidence; after reload, temporary source has been deleted and the user must upload the HTML again. Recover recent failed tasks with their reason and upload action.
